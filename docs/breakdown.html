One timer for the whole app

A menu bar app that ticks every second all day is a battery bug. Cue schedules a single timer at the next minute boundary and re-aims it after every tick.
Timer fires
at the minute boundary, tolerance 0.25s
→
now = Clock.now()
wall clock plus a demo offset
→
store.tick(now:)
poll Google if 180s stale, or reload EventKit at day rollover
→
evaluateAlerts()
close a finished alert, raise the next one
→
scheduleNextTick()
next minute, or a sooner snooze deadline

Also kicks the tick

  • NSWorkspace.didWakeNotification → refresh with age 0, then tick
  • store.$meetings changing → tick, so the menu bar repaints
  • Opening the popover → refreshIfStale(60)
  • .EKEventStoreChanged → reload, macOS source only

The only per-second work

  • TimelineView(.periodic, by: 1) inside the overlay countdown ring
  • The same, inside the mini card — and only while it is visible
  • The status item image is redrawn only when BarState actually differs from the last one rendered
  • The popover's SwiftUI tree is built on open and dropped on close, so nothing sits in memory while hidden
03

The alert flow

One phase per meeting, held in [String: Phase] keyed by id|start so a recurring event gets a fresh phase each occurrence.

What raises it

  • Only meetings that actually have a call link
  • Window is start − 60s to start + 5min
  • One at a time: a new alert marks the previous one dismissed unless it was joined
  • Off entirely if alertsEnabled is false

Minimize vs dismiss

  • Minimize keeps the meeting alive as a draggable card — esc, a click on the scrim, or losing focus to another app all mean this
  • Dismiss is the only way to silence it for good
  • The overlay leaves the menu bar uncovered and sits one level below .statusBar

Joining

  • Joiner.open records which app handled the URL, so “Back to call” can re-activate it
  • Zoom links are rewritten to zoommtg:// when the native app is installed, skipping the browser hop
  • No link? Falls through to opening the event in Google Calendar or Calendar.app
04

The menu bar item

Not a label — a NSImage drawn by hand in BarArt: a filled capsule, a glyph or a progress ring, and monospaced-digit text.
.idle — nothing left today, or nothing within reach. Plain SF Symbol template, so it follows the menu bar tint.
Standup at 10:30
.later(m) — more than an hour away, still today. Title clipped to whole words under ~18 characters.
Standup in 42m
.soon(m, 42) — inside the hour. The ring fills as minutes / 60.
Standup in 7m
.soon, under soonMinutes = 10 — the capsule turns orange.
Join Standup
.join(m) — T−60s to T+5min. A plain left-click joins the call directly; hold ⌥ to open the popover instead.
12m left
.during(m, 12) — in progress. The ring is elapsed fraction, quantised to 1/50ths so the image is redrawn at most 50 times per meeting.
2m left
.during, under wrapUpMinutes = 3 — orange, matching the mini card's wrap-up state.

The whole thing degrades gracefully: if a menu bar manager like Ice or Bartender hides the item, or the notch pushes it off-screen, PopoverController notices the anchor isn't in the menu bar and opens at the top-right of the screen instead.

Five surfaces

All of them are borderless NSPanels — FloatingPanel — that can take keyboard focus without activating the app, Spotlight-style.

Hover peek.popUpMenu, non-keyablefits content ignoresMouseEvents, so running down the list just slides the card along. 0.35s to appear, 0.12s grace on leaving. Sits left of the popover, flips right if there's no room.

Fades are 0.18s in and 0.14s out, and both collapse to zero when accessibilityDisplayShouldReduceMotion is set. Shadows are invalidated a run-loop hop after the first layout, which is the fix for AppKit drawing a stale shadow around a freshly-sized SwiftUI panel.

What the hero picks

  • A meeting starting within 15 minutes beats one already in progress
  • Otherwise the latest-started live meeting wins
  • With nothing left: “No more meetings today / Enjoy the quiet.”
  • The access state short-circuits all of it — .denied, .unknown and .needsGoogle each have their own screen

Keyboard

  • ⌘N — new event
  • esc — back one route, then close
  • ⌘↩ / ↩ — create or save, from inside the text field
  • Focus rings are disabled throughout; the hints are drawn as KeyHint pills instead

Adding an event is one text field

No form. You type a sentence, Cue tints the parts it understood, and everything else is a chip you can correct.
Design sync with Priya tomorrow at 3pm 45m
understood, and removed from the title → title “Design sync” → guest priya.shah@… → start tomorrow 15:00 → length 45 min
1 · durations
45m, 1.5 hrs, half an hour, an hour
→
2 · emails
matched against your contacts, else taken as-is
→
3 · the date
NSDataDetector over the text with steps 1–2 blanked out
→
4 · names
words after with, two-word then one-word, against recent contacts
→
5 · the title
what's left, with dangling connectors trimmed

Order is the whole trick. Durations and emails are masked out before the date detector runs, so 45m is read as a length and not as 45 minutes past the hour, and name@host.com doesn't look like a date. A name after with that matches nobody lands in unknownNames and the UI asks for their email rather than silently dropping it — and only the first word of each name slot counts, so “with Sanket about Q4” asks about Sanket, not about Q4.

A typed time already in the past rolls to tomorrow unless you said “today”. With no time at all, the day is today before 17:00 and tomorrow after. Suggestions are quarter-hour starts only.

Find a time

Google's free/busy endpoint, one lane per invitee plus yours. Busy blocks are merged, then the gaps long enough for the meeting are the candidates.
You
Priya
Rahul
you asked
Cue picks
09:0011:0013:0015:0017:0019:00
busy 3pm clashes with You and Priya 14:15 — the closest 45-minute gap

Picking the slot

  • Working hours are 09:00–19:00, never earlier than now rounded up to the quarter
  • Each free stretch yields its first quarter-hour start, and — when you asked for a time — the latest start that still fits, which is usually the closer answer
  • Sorted by distance from what you asked for; the top three are offered

Keeping it cheap

  • Queries are debounced 250 ms, so typing doesn't fire a request per keystroke
  • Results cached 5 minutes per calendar|day
  • The in-flight task is cancelled when the lane set or the day changes
  • A lane Google won't share is marked unavailable and excluded from the merge rather than treated as free

Where the names come from

  • Attendees of your own meetings, −60 days to +14 days
  • Counted by how often you meet them, most frequent first
  • Rooms, resources and yourself filtered out
  • Refreshed at most once every 12 hours, on a trimmed fields=attendees(...) request
09

Where meetings come from

Two interchangeable sources behind one @Published [Meeting]. The rest of the app can't tell which is live.

Google Calendar — the default

  • calendarList, paged at 250, then the calendars ticked in Google's own sidebar — with a per-calendar override in Cue's settings
  • Events fetched in parallel via a ThrowingTaskGroup, results re-sorted into a deterministic order with your primary calendar first
  • De-duplicated on iCalUID|start, so an event on two calendars keeps your own calendar's colour
  • Window is startOfDay(today) → +2 days, singleEvents=true so recurrences arrive expanded
  • Polled every 180 s, plus on wake, plus on popover open if older than 60 s
  • Write path: create, patch, delete and RSVP, all with sendUpdates=all

macOS Calendar — opt-in from the gear menu

  • EKEventStore.requestFullAccessToEvents, same two-day window via predicateForEvents
  • No polling at all — reloads only on .EKEventStoreChanged or at the day rollover
  • Colour comes from the EKCalendar; links are sniffed out of the URL, location and notes
  • Read-only: no create, edit, RSVP or find-a-time, since those are built on Google's API
  • Whatever Internet Accounts syncs is what you get — Exchange, iCloud, a subscribed ICS
↓

What never reaches the list

all-day eventscancelledanything you declined working-location blocksout-of-officeduplicate copies across calendars locations that are really “Microsoft Teams Meeting”

Meetings are compared field-by-field before publishing, so a poll that returns identical data doesn't touch @Published and doesn't repaint anything. On a network error the last good list is kept and the next attempt is pulled in to a minute from now instead of waiting out the full poll interval.

Sign-in, by hand

OAuth for installed apps: a browser round-trip, a loopback redirect, PKCE. No Google SDK, no embedded web view.
1 · listen
NWListener on 127.0.0.1, OS-assigned port, loopback interface only
→
2 · challenge
32 random bytes from SecRandomCopyBytes, SHA-256, base64url — S256
→
3 · consent
the real Google page, in the real browser, with the real URL bar
→
4 · redirect
code + state arrive on the loopback socket; the listener answers with a styled “you're signed in” page
→
5 · exchange
state compared, then code + verifier swapped for tokens
→
6 · store
refresh token to the Keychain, access token to memory

Kept off disk on purpose

  • URLSessionConfiguration.ephemeral, urlCache = nil — no response cache, no cookie jar, 20 s timeout
  • Refresh token in the Keychain as kSecAttrAccessibleAfterFirstUnlock, service com.eshaanshah.cue.google
  • Access token lives only in memory, and expires 60 s early so a request never races the boundary
  • Every response is trimmed with a fields= mask, so a poll is a few KB rather than a few hundred
  • Signing out revokes the token at Google and deletes the Keychain item
  • The id_token payload is read without verifying the signature — it came straight from Google over TLS, and it is only used for the account label

What can go wrong, and what you see

  • invalid_grant → .expired: the Keychain item is dropped and the popover asks you to sign in again
  • 403 insufficient scope → .needsWriteAccess, routing straight to PermissionView
  • Granted scopes are remembered, so an older read-only sign-in is detected before a write is attempted rather than after it fails
  • Anything else offline-ish: the current list stands and the retry is pulled forward to a minute
  • While the Google Cloud project is in Testing, Google forces a re-consent every 7 days — a platform limit, not a bug
scope · calendar.events scope · calendar.readonly scope · email read-only until you first add or edit google-oauth.json is git-ignored

Writing back

Four operations, one gate. Every one of them funnels through CalendarStore.write, which checks the scope, then forces a refetch so the UI can't drift from Google.
OperationRequestCare taken
createPOST /eventsGoogle Meet asked for via conferenceData.createRequest with a fresh request id; conferenceDataVersion=1
editPATCH /events/{id}Only keys that actually changed are sent — title, start/end, description, attendees — diffed against the meeting you opened
RSVPPATCH attendeesGoogle wants the whole guest list back, so it is rewritten with only your own responseStatus touched — and rooms stay in the list, so replying never cancels the room booking
deleteDELETE /events/{id}Removed from the local list first so the popover reacts instantly, then confirmed against the server

All four pass sendUpdates=all, so guests get the mail Google would normally send. canModify is computed per meeting from the calendar's accessRole plus whether you organise it or guestsCanModify is set — the edit button simply isn't there when it would fail.

Build, demo, snapshot

A 21-line shell script instead of an Xcode project. The two debug modes exist so the UI can be checked without waiting for a real meeting.
./build.sh
Release build, stripped, Info.plist and Cue.icns copied in, google-oauth.json folded into Resources, ad-hoc signed → build/Cue.app, 2.4 MB. Warns rather than fails when the OAuth client is missing.
open -n build/Cue.app --args --demo 10:18 --show popover
Demo mode: nine fixed meetings matching the design boards, Clock.offset pretending it's 10:18, synthetic free/busy for Priya and Rahul, and Joiner.dryRun so no real call link is ever opened. The Keychain is never touched, so there's no prompt.
open -n build/Cue.app --args --demo 10:29:10
Sits 50 seconds before standup, so the overlay fires on its own and the whole alert flow can be watched end to end.
.build/debug/Cue --demo --snapshot snaps
Renders every surface offscreen through ImageRenderer at 2×, in light and dark, onto the mockups' gradient backdrop, then exit(0). Twenty-two PNGs, no window ever shown — this is how the build is checked against mockups/.
ditto build/Cue.app /Applications/Cue.app
Install. Because the signature is ad-hoc, macOS re-asks for Keychain and calendar access after each rebuild — answer Always Allow.

The snapshot path is worth noting as a design decision: rather than screenshot a running app, the same SwiftUI views are rendered headless at a frozen clock. That makes every state — including ones that only exist for 60 seconds — reviewable in a diff.
